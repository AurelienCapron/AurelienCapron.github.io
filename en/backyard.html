01

One hour to finish and restart

A 6.706 km lap starts every hour. Crossing the line validates the lap and determines how much rest is left before the next start. A runner who finishes in 48 minutes has 12 minutes to recover.

The timing system must associate each crossing with the right bib and lap, including when an operator enters it just after the hour changes.

Watch a lap start
02

Two desks, one recorded finish

Each desk sends its input to the same Flask server on the local network. If two volunteers enter bib 42 for the same lap, a lock makes the server process the requests in sequence. The first entry is written to the CSV; the second receives a duplicate response.

During the first 60 seconds of a new lap, the software can assign a late entry to the previous lap if the runner was still eligible. An undo action also lets an operator correct a mistaken entry.

View the network architecture
03

A view for each role

Volunteers enter finishes. The announcer follows the field to call arrivals. The TV display gives spectators an overview, while runners can look up statistics by bib number. The monitoring screens poll the server for updates.

04

Keeping the results after the final lap

The finish log records the bib, lap, arrival time, lap time, rest and status. These records can be used to rebuild the race state. Runners are ranked by validated laps, then by average lap time when tied.

An Excel export lets organisers retain and review results after the event.
